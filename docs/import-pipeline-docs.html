ĐẶC TẢ LUỒNG NHẬP DỮ LIỆU & IMPORT PIPELINE V3

Tài liệu kiến trúc chi tiết mô tả cách hệ thống tự động nhận dạng cấu trúc tập tin, giải mã bảng mã ký tự Nhật Bản, bóc tách các dòng giao dịch từ tệp CSV/PDF của Rakuten Pay và PayPay, lọc bỏ các giao dịch trùng lắp, tự động gán phân cấp danh mục (Auto-Categorization), và đồng bộ hóa bất đồng bộ với cơ sở dữ liệu Supabase.

1. Tổng quan Luồng Ingest Giao dịch

Trang Nhập dữ liệu (app/import/page.tsx) đóng vai trò là một Ingestion Pipeline Client-side mạnh mẽ. Người dùng có thể kéo thả bất kỳ tập tin xuất ra từ các ứng dụng thanh toán phổ biến như PayPay, Rakuten Pay hay ngân hàng lớn (SMBC, MUFG, VCB, MBBank). Hệ thống tiến hành xử lý hoàn toàn trên trình duyệt để bảo mật quyền riêng tư tài chính, hiển thị bảng kiểm duyệt (Review Table) trước khi thực hiện ghi dữ liệu vĩnh viễn (Commit).

1
File Selection & Encoding Analysis
Người dùng chọn file CSV hoặc PDF. Hệ thống kiểm tra BOM (Byte Order Mark) để tự động quyết định giải mã bảng mã Shift-JIS hay UTF-8.
2
Provider & Format Auto-Detection
Hệ thống quét dòng tiêu đề hoặc đuôi mở rộng để nhận diện nhà cung cấp (PayPay, Rakuten Pay, SMBC...) mà không bắt buộc chọn trước.
3
Parsing & Normalization (Extracting Values)
Thực hiện regex bóc tách ngày tháng (Date), chuyển đổi đơn vị Yên (¥) thành số âm hoặc dương phù hợp, xử lý tên cửa hàng.
4
Smart Categorization & Deduplication Rule Matching
Áp dụng bộ quy tắc Regex gán danh mục mặc định. Đối chiếu các chuỗi chuyển khoản nạp tiền (Top-up) để chuyển thành giao dịch Transfer.
5
Zustand Client Store & Batch Supabase DB Upsert
Dữ liệu được đẩy vào store giao diện và gọi hàm upsert() chia theo lô (Batch) 10 bản ghi để cập nhật cơ sở dữ liệu Supabase.

2. Cơ chế Tự động hóa Pipeline (Auto-Detection Engine)

Hệ thống tối ưu hóa UX bằng cách tự động hóa 3 khâu phức tạp nhất trong việc xử lý tệp tin thô từ Nhật Bản:

Vấn đề kỹ thuật: Các file CSV xuất từ các hệ thống tài chính Nhật Bản cũ thường sử dụng mã hóa Shift-JIS, trong khi các hệ thống hiện đại xuất file UTF-8. Nếu đọc không đúng, toàn bộ tiếng Nhật (tên cửa hàng, loại giao dịch) sẽ bị lỗi font (Mojibake - 文字化け).

Hệ thống đọc file dưới dạng Buffer nhị phân (ArrayBuffer) và chạy thuật toán kiểm tra mã hóa sau:

// Đọc file nhị phân trong file:///Users/Leonardo%20Thang/Code/leo-walletly/features/import/parsers/index.ts
async function readFileText(file: File): Promise<string> {
  const buffer = await file.arrayBuffer()
  const bytes  = new Uint8Array(buffer)
  
  // 1. Kiểm tra UTF-8 Byte Order Mark (BOM: EF BB BF)
  const hasUtf8Bom = bytes[0] === 0xef && bytes[1] === 0xbb && bytes[2] === 0xbf
  let text: string
  
  if (hasUtf8Bom) {
    text = new TextDecoder('utf-8').decode(buffer)
  } else {
    // 2. Thử giải mã Shift-JIS trước
    const sjis = new TextDecoder('shift-jis').decode(buffer)
    // Nếu kết quả chứa các kí tự lỗi hoặc không hợp lệ, fallback về UTF-8
    text = sjis.includes('') ? new TextDecoder('utf-8').decode(buffer) : sjis
  }
  return text.replace(/^\uFEFF/, '') // Loại bỏ ký tự BOM nếu có ở đầu chuỗi
}

Khi người dùng tải lên tập tin CSV, hệ thống trích xuất dòng đầu tiên chứa danh sách các cột tiêu đề (Headers) và quét qua bộ từ khóa đặc trưng (Signature Columns) để tự định vị nhà cung cấp:

Tên Provider Cột đặc trưng (Signature Headers) Mã Provider (DB)
Rakuten Pay CSV 利用日 VÀ 利用金額 rakuten_pay
PayPay App CSV 取引日時 VÀ 残高 VÀ 支払い金額 paypay
PayPay Card CSV Chứa cột 利用日/キャンセル日 HOẶC (利用店名 VÀ 支払区分) paypay_card
SMBC Card CSV Chứa cột お取り扱い内容 HOẶC お支払い金額 smbc
MUFG Bank CSV 摘要内容 VÀ 支払い金額 mufg
Vietcombank CSV Chứa cột ngày gd HOẶC phát sinh vcb
MB Bank CSV Chứa cột ngày giao dịch mbbank

Trong quá trình phân tích, hệ thống chạy chuỗi ký tự mô tả giao dịch (description) qua một bộ động cơ regex biểu thức chính quy (Regex Pattern Engine) để gán danh mục chi tiêu sơ cấp (Legacy Categories): 

// Regex gán danh mục tự động dựa trên từ khóa tiếng Nhật & Anh
function guessCategory(desc: string): Category {
  const d = desc.toLowerCase()
  
  if (/コンビニ|スーパー|マート|食|レストラン|カフェ|ファミマ|ローソン|セブン|吉野家|すき家|マクドナルド|ケンタ|pizza|すし|cafe|restaurant|food|grocery/.test(d))
    return 'food'
    
  if (/電車|バス|鉄道|jr|タクシー|ガソリン|駐車|エキ|metro|subway|交通|新幹線|taxi|train|transit/.test(d))
    return 'transport'
    
  if (/amazon|楽天|ヤフー|zara|ユニクロ|ネット|通販|ショッピング|shopping|store|shop/.test(d))
    return 'shopping'
    
  if (/映画|ゲーム|娯楽|カラオケ|ネットフリックス|netflix|spotify|アミューズ|game|cinema|entertainment/.test(d))
    return 'entertainment'
    
  if (/薬|ドラッグ|病院|クリニック|医|健康|fitness|gym|ジム|pharmacy|hospital|clinic/.test(d))
    return 'health'
    
  if (/電気|ガス|水道|光熱|通信|ネット|電話|ntt|softbank|docomo|au|mobile|internet|utility/.test(d))
    return 'utilities'
    
  return 'other'
}

3. Xử lý Rakuten Pay (CSV & PDF)

Hệ thống hỗ trợ cả file bảng kê giao dịch CSV lẫn tệp hóa đơn thanh toán PDF trực tiếp của Rakuten Pay.

🔴 Rakuten Pay CSV Parser

Trích xuất các giao dịch thanh toán qua ví điện tử Rakuten Pay hoặc thẻ tín dụng liên kết.

  • Các cột ánh xạ chính: 利用日 (Ngày sử dụng), 利用店名・商品名 (Tên cửa hàng/mô tả), 利用金額（税込） (Số tiền giao dịch), 備考 (Ghi chú).
  • Xử lý số tiền: Loại bỏ kí tự tiền tệ ¥, dấu phẩy phân tách nghìn , và chữ 円. Các khoản thanh toán luôn được tự động nhân với hệ số âm (ví dụ: chi tiêu 1,000 Yên → lưu trữ là -1000).
📄 Rakuten Card PDF Parser

Bóc tách tệp PDF "ご利用代金請求明細書" (Hóa đơn yêu cầu thanh toán thẻ tín dụng Rakuten).

  • Nhận diện dòng: Quét các dòng văn bản bắt đầu bằng định dạng ngày YYYY/MM/DD.
  • Tách tên cửa hàng: Sử dụng các mốc neo 本人 (Thẻ chính) hoặc 家族 (Thẻ phụ) để cắt chuỗi mô tả ở giữa làm tên cửa hàng.
  • Bóc tách số tiền thanh toán: Tìm mốc neo phân loại thanh toán (払い hoặc 一括). Hệ thống bóc ra 5 cột số phía sau và lấy cột thứ 4 làm Số tiền yêu cầu thanh toán tháng này (当月請求額).
Ví dụ cấu trúc dòng PDF của Rakuten Card & Giải thuật Cắt chuỗi
Dòng văn bản thô trích xuất từ PDF:
"2026/04/01 楽天モバイル通信料 本人 * 1 回払い 3435 0 3435 3435 0"

Thuật toán Parser xử lý (file:///Users/Leonardo%20Thang/Code/leo-walletly/features/import/parsers/rakuten_pay_pdf.ts):
1. Nhận diện ngày: "2026/04/01" -> Chuỗi Date chuẩn: "2026-04-01"
2. Cắt chuỗi Store bằng mốc "本人":
   rest = "楽天モバイル通信料 本人 * 1 回払い 3435 0 3435 3435 0"
   storeName = rest.slice(0, index_of("本人")) -> "楽天モバイル通信料"
3. Tìm kiếm cụm từ khóa phương thức thanh toán "払い" để lấy phần số tiền:
   amountSection = " 3435 0 3435 3435 0"
   Trích xuất mảng các số: nums = [3435, 0, 3435, 3435, 0]
4. Lấy cột số thứ 4 (chỉ số index 3) làm số tiền thanh toán:
   billingAmount = nums[3] = 3435 -> Lưu trữ: -3435 (Expense)

5. Sơ đồ Ánh xạ Trường (Source Columns to DB Columns)

Dưới đây là bảng đặc tả mô tả cách các trường thông tin trong tệp nguồn CSV/PDF được chuyển đổi và lưu trữ vào cấu trúc bảng cơ sở dữ liệu transactions (kiểu Transaction v3):

Raw Source Field (CSV/PDF) Destination Property (React Code) Database Column (Supabase) Kiểu Dữ Liệu & Quy Tắc Xử Lý
(Auto-Generated) id id uuid. Tạo mã UUIDv4 ngẫu nhiên ngay tại trình duyệt để làm khóa chính duy nhất.
利用日 / 取引日時 / Date & Time transactionDate transaction_date date. Chuyển đổi mọi định dạng Nhật Bản (như 2026/04/01 12:30 hoặc 2026年04月01日) về chuẩn ISO YYYY-MM-DD. Lấy phần ngày, lược bỏ giờ.
利用店名・商品名 / Business Name / 利用店名 description description text. Lưu tên cửa hàng hoặc tên giao dịch. Nếu rỗng, mặc định là "不明" (Không rõ) hoặc tên loại giao dịch.
利用金額 / 金額（円） / Amount Outgoing / Incoming amount amount numeric.
  • Khoản chi tiêu: Số âm (ví dụ: -3435).
  • Khoản thu nhập/Hoàn tiền: Số dương (ví dụ: 500).
(Auto-Guessed from Description) categoryId category_id text/uuid. Khớp từ khóa để gán mã danh mục (ví dụ: food, shopping, transport, utilities).
(Selected Provider value) paymentInstrumentId payment_instrument_id text. Lưu định danh loại tài khoản (ví dụ: paypay, paypay_card, rakuten_pay).
備考 / メモ notes notes text. Lưu thông tin ghi chú kèm theo giao dịch trong CSV (nếu có).
(Tất cả các cột còn lại) metadata metadata jsonb. Lưu toàn bộ dòng dữ liệu CSV gốc dưới dạng Object để làm dữ liệu đối soát phục vụ kiểm toán tài chính sau này.
(Tĩnh) status status text. Gán mặc định là 'posted'.
(Tĩnh) isReconciled is_reconciled boolean. Gán mặc định là false để người dùng đối soát thủ công nếu cần.
(Tĩnh) currencyCode currency_code text. Gán mặc định là 'JPY' đối với các hóa đơn thanh toán Nhật Bản.

6. Giải Thuật Tránh Tính Trùng Số Liệu (Double-Counting Prevention)

Rủi ro tài chính FinTech: Khi người dùng nạp tiền từ thẻ tín dụng PayPay Card vào ví điện tử PayPay:
1. Trong sao kê thẻ PayPay Card sẽ xuất hiện dòng chi tiêu: "PayPay残高チャージ" (Chi tiêu nạp tiền).
2. Trong sao kê ví PayPay App sẽ xuất hiện dòng thu nhập: "チャージ" (Nạp tiền vào ví).
Nếu tính cả hai dòng này vào báo cáo, tổng chi tiêu của người dùng sẽ bị nhân đôi một cách ảo, gây sai lệch báo cáo dòng tiền nghiêm trọng.

Hệ thống xử lý bài toán này thông qua thuật toán lọc loại giao dịch (resolveType) phân bổ như sau:

📱 PayPay App CSV Rules

Kiểm tra cột 取引種別 (Loại giao dịch): 

if (/チャージ|charge|top.?up/.test(typeStr)) 
  return 'transfer' // Ghi nhận là Chuyển khoản nội bộ
if (/送金|振込|transfer|send/.test(typeStr)) 
  return 'transfer' // Ghi nhận là Chuyển khoản nội bộ
💳 PayPay Card CSV Rules

Kiểm tra cột 利用店名・商品名 (Tên cửa hàng): 

const TRANSFER_RE = /paypay残高|残高チャージ|paypayチャージ/i
if (TRANSFER_RE.test(storeName)) 
  return 'transfer' // Ghi nhận là Chuyển khoản nội bộ
Kết quả: Cả hai dòng đối ứng trên đều được đánh dấu loại giao dịch là transfer trong database. Các công cụ biểu đồ báo cáo tài chính sẽ loại bỏ các dòng có transaction_type = 'transfer' khi tính tổng chi tiêu thực tế, giải quyết triệt để vấn đề tính trùng số liệu.

7. Cơ chế Ghi Dữ Liệu & Đồng Bộ Hóa Supabase (Data Sync Pipeline)

Để mang lại trải nghiệm người dùng tối ưu, hệ thống sử dụng kiến trúc ghi dữ liệu 2 giai đoạn (Two-Stage Commit Pipeline):

Giai đoạn 1: Đọc và Hiển thị Preview tạm thời trên Trình duyệt

Tệp tin được phân tích hoàn toàn client-side bằng thư viện papaparse (cho CSV) hoặc thư viện xử lý PDF. Kết quả được lưu vào biến trạng thái cục bộ result trong React component.

  • Người dùng có thể tick chọn hoặc bỏ chọn từng dòng giao dịch trên bảng.
  • Các thông số tổng lượng thu, chi, số dư ròng được cập nhật liên tục dựa trên các dòng được chọn.
  • Chưa có bất kỳ dữ liệu nào được ghi xuống database ở giai đoạn này. Người dùng có thể bấm Hủy (Reset) để xóa sạch trạng thái tạm thời này.
Giai đoạn 2: Lưu vào Zustand Store và Đồng bộ hàng loạt xuống Supabase

Khi người dùng bấm nút "Nhập [X] giao dịch", hệ thống gọi hàm addTransactions(toAdd) của useTransactionsStore. Quá trình xử lý diễn ra như sau: 

// Xử lý trong file:///Users/Leonardo%20Thang/Code/leo-walletly/stores/transactions.ts
addTransactions: (txns) => {
  const currentLedger = useLedgerStore.getState().currentLedger
  
  // 1. Ánh xạ tenant context của Ledger hiện tại vào giao dịch
  const processedTxns = txns.map(tx => ({
    ...tx,
    ledgerId: tx.ledgerId || currentLedger?.id || '',
    workspaceId: tx.workspaceId || currentLedger?.workspace_id || '',
    organizationId: tx.organizationId || currentLedger?.organization_id || '',
  }))

  // 2. Cập nhật state local ngay lập tức trên UI (Optimistic Update)
  set((s) => {
    const existing = new Set(s.transactions.map((t) => t.id))
    const fresh = processedTxns.filter((t) => !existing.has(t.id))
    return { transactions: [...s.transactions, ...fresh] }
  })

  // 3. Đồng bộ bất đồng bộ xuống bảng "transactions" trong Supabase DB
  supabase.auth.getUser().then(async ({ data: { user } }) => {
    if (!user) return

    const toInsert = processedTxns.map(t => ({
      id:                      t.id,
      organization_id:         t.organizationId,
      workspace_id:            t.workspaceId,
      ledger_id:               t.ledgerId,
      payment_instrument_id:   t.paymentInstrumentId || null,
      category_id:             t.categoryId || null,
      status:                  t.status || 'posted',
      transaction_type:        t.transactionType,
      source:                  t.source || 'manual',
      description:             t.description || null,
      transaction_date:        t.transactionDate,
      amount:                  t.amount,
      currency_code:           t.currencyCode || 'JPY',
      metadata:                t.metadata || {},
    }))

    // Sử dụng câu lệnh upsert để ghi đè nếu trùng ID hoặc chèn mới nếu chưa có
    const { error } = await supabase.from('transactions').upsert(toInsert)
    if (error) {
      console.error('Lỗi đồng bộ Supabase:', error.message)
    }
  })
}
